TIER 1

Highest value per unit of work

Ordered by how much each one improves the experience against how much has to be built.

01

Snap heard codes to codes that actually exist

The biggest accuracy win available, and it needs no new data — 74,706 ICD-10 codes, 9,435 HCPCS and the MPFS table are already installed. When the recognizer returns something code-shaped, validate it against those tables and snap to the nearest valid code, then refuse when two candidates are equally close rather than picking one. A silently substituted code is the worst failure this interface can have; "did you mean 99213 or 99214?" is the correct behaviour.

plugs into src/speech/spoken-codes.ts → src/tools/healthcare/datasets.ts
02

Bias the recognizer with the practice's own vocabulary

Every engine takes a hint list — Deepgram keyterms, OpenAI's prompt, Whisper's --prompt, SpeechGrammarList in the browser. Build it from the codes this practice actually bills, its payer names and its rendering providers. Generic speech recognition has never heard of "Availity" or "J1885"; a hinted recognizer gets both right.

plugs into claim history in the store → each provider's transcribe call
03

Speak the first sentence while the rest is still generating

Perceived latency is dominated by waiting for a complete answer before any sound. Chunk the text_delta stream by sentence, normalize and speak each chunk as it closes. Turns a six-second silence into a 700 ms one and costs no model change.

plugs into the text_delta handler in web/public/voice.js
04

Spoken tool narration

tool_call already streams. Saying "checking NCCI edits" while a scrub runs is the difference between a system that seems hung and one that seems to be working. One clause, the tool's human label, and never the arguments.

plugs into the tool_call event, already on the wire
05

Run the PHI gate on the transcript, before the model sees it

The identifier gate exists for documents and the access log exists. A spoken member ID currently reaches the model unexamined. Run the same scan on every transcript, redact at the same choke point, and log the access. This is the item that decides whether voice is usable anywhere near real data.

plugs into src/tenancy/access-log.ts · src/ingest/ identifier scan
TIER 2

Intelligent rather than merely hands-free

Where it stops being dictation and starts being a colleague.

06

Screen-aware reference resolution

"Appeal that one." Voice without visual context cannot resolve it. The console already renders structured tool views and a canvas; pass the active view and the current selection into the turn so pronouns resolve to the row on screen. This is the single change that separates conversation from command entry.

plugs into ToolView + canvas state → the turn payload
07

Worklist mode

A denial worklist read one item at a time, with "appeal it", "next", "skip" and "why was it denied" as the entire vocabulary. This is the actual productivity story — a coder with both hands in a chart clearing a worklist by voice — and every underlying tool already exists.

plugs into worklist_ and appeal_draft tools, composed
08

Brief mode, and knowing when to use it

A spoken answer should be the verdict, not the essay. Add a verbosity setting and default spoken replies to headline-plus-number, with "tell me more" expanding. speakableSummary() already does the hard part.

plugs into src/speech/speakable.ts
09

Speculative lookups while the user is still talking

Interim recognition results arrive before the utterance ends. When an interim transcript already contains an unambiguous code, start the read-only lookup immediately and discard it if the final transcript disagrees. Safe by construction, because it is restricted to safe-risk tools.

plugs into interim results → assessRisk === "safe" tools only
10

Voice-first morning briefing

The KPI, aging, timely-filing and policy-watch tools all exist. A spoken two-minute briefing — "three claims hit timely filing inside five days, one payer changed a policy on a code you bill" — is the highest-value proactive use of speech in this product, and it is mostly composition.

plugs into kpi_dashboard · timely_filing_ · research_payer_policy
TIER 3

Larger projects, worth naming

Real scope. Listed so they are decisions rather than surprises.

11

Ambient encounter capture to superbill

Listening to a clinical encounter and producing coded output is the most valuable thing voice can do in healthcare, and it is a different product: per-state consent, retention, accuracy liability, and a real PHI mode. The documentation-native CDI module is the right foundation — but do not start here.

plugs into src/voice/consent.ts (all-party states already modelled)
12

Speaker verification before destructive actions

A voice interface removes the keyboard as an implicit authentication factor. Anything that submits a claim or writes to a payer should require a confirmed speaker, or fall back to the screen.

plugs into the approval choke point in the tool registry
13

On-device wake word

Continuous speech recognition to detect one phrase is expensive and, off the machine, an exposure. A dedicated wake-word model fixes both, and is what would let always-on mode run under the local and cloud engines instead of browser only.

plugs into the wake-word path in web/public/voice.js
14

Voice cases in the eval harness

The harness already measures tool selection. Extend it to speech: word error rate on a healthcare phrase set, code-recognition accuracy, and tool selection from spoken input. A low score is the finding, not a reason to tune the cases — the same discipline the existing harness already holds.

plugs into src/eval/cases.ts
—

What I would not build

✕ Reading tables aloud. Already prevented in the normalizer. A spoken table is noise — say the headline and highlight the row on screen.
✕ Voice as the only route to an approval. The dialog stays the authority; speech is a second way to answer it, never a replacement for seeing what is about to run.
✕ Always-on by default. A hot microphone in a room where patients are discussed records the room, not the request.
Engine choice decides where audio goes: only the local engine keeps it on the machine. The browser engine sends captured audio to Google and the cloud engine to a vendor — both are fine for the de-identified posture this build declares, and wrong for anything else.
